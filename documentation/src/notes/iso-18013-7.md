## Technical Report: ISO/IEC 18013-7 Request Building Mechanisms

ISO/IEC 18013-7 standardizes how mobile driving licenses (mDLs) and generic mDocs are presented over the internet, extending the proximity-based protocols of ISO/IEC 18013-5. The standard defines three distinct annexes for remote presentation, each requiring a fundamentally different approach to building the Verifier's request.

### 1. Annex A: REST API (Device Retrieval)

Annex A relies on an HTTP-based remote device retrieval paradigm. It essentially takes the core ISO 18013-5 CBOR/COSE cryptographic structures and routes them over a REST API rather than a local BLE/NFC connection.

* **Request Construction:** The Verifier application builds an HTTP POST request.
* **Payload Format:** The body contains a CBOR-encoded `DeviceRequest` exactly as specified in ISO/IEC 18013-5. This includes the requested document types, namespaces, and specific data elements, wrapped in session encryption.
* **Transport:** The request is sent directly to a server acting as a proxy for the mDL, or directly to a wallet's exposed endpoint.
* **Developer Impact:** Implementing Annex A in code requires heavy lifting in CBOR parsing, COSE cryptography, and session key establishment directly at the network layer.

### 2. Annex B: OpenID4VP (OpenID for Verifiable Presentations)

Annex B standardizes mDoc presentation over the OAuth 2.0 / OpenID Connect framework. This is the dominant protocol in the broader verifiable credential ecosystem.

* **Request Construction:** The Verifier acts as an OAuth 2.0 Client. The request is built as an Authorization Request URI (typically leveraging SIOPv2/OID4VP).
* **Payload Format:** The core of the request is a `presentation_definition` object (using Presentation Exchange - PEX). This JSON object maps the required mDoc claims (e.g., `org.iso.18013.5.1` namespace) to the Verifier's requirements.
* **Transport:** The request is often delivered via a `request_uri` pointing to a JWT Secured Authorization Request (JAR). The wallet retrieves this, gathers user consent, and sends an encrypted `vp_token` containing the mDoc `DeviceResponse` to the Verifier's `response_uri` via HTTP `direct_post`.
* **Developer Impact:** Requires robust JWT/JWE handling and implementation of Presentation Exchange logic, but avoids the need to build custom network routing for CBOR payloads.

### 3. Annex C: W3C Digital Credentials API (DC API)

Annex C moves the request mechanism out of the backend network layer and into the client-side browser using a standardized Web API.

* **Request Construction:** The request is built in client-side JavaScript using the `navigator.credentials.get()` method.
* **Payload Format:** The request specifies a `digital` credential type. It encapsulates the protocol-specific request profile (e.g., nesting an OID4VP request or a direct `org-iso-mdoc` profile) directly inside the browser API call.
* **Transport:** The browser and the underlying operating system natively handle wallet invocation. For cross-device flows, the OS establishes a secure tunnel (utilizing BLE proximity checks and relay servers like `cable.ua5v.com`) to pass the request to the wallet.
* **Developer Impact:** Drastically reduces Verifier UX complexity. Developers rely on the browser to handle context switching, session binding, and cross-device tunneling.

## OpenID4VP HAIP vs. EU-AV Schemes

While both the High Assurance Interoperability Profile (HAIP) and the EU Age Verification (EU-AV) blueprint leverage OpenID4VP, they have fundamentally different threat models and architectural rules. Implementing these in code requires distinct request parameter configurations.

### OpenID4VP HAIP (High Assurance Interoperability Profile)

Managed by the OpenID Foundation, HAIP is designed for generalized, high-security credential exchange.

* **Integrity Protection:** HAIP strictly relies on JWT Secured Authorization Requests (JAR) to protect the Verifier's request integrity.
* **Trust Model:** It assumes the existence of Relying Party (RP) Trust Lists. The Wallet uses PKI/X.509 certificates to verify the Verifier's identity before presenting the mDoc.
* **Response:** Demands highly encrypted responses utilizing `direct_post.jwt`.

### EU-AV Scheme (EU Age Verification Blueprint)

Driven by the Digital Services Act (DSA), the EU-AV blueprint is an EUDIW-specific profile designed *exclusively* for privacy-preserving, anonymous age checks (e.g., proving "Over 18" for online services).

* **Privacy by Design:** Employs Zero-Knowledge Proofs (ZKPs) operating on a double-blind model. The Verifier receives a cryptographic binary "yes/no" without learning the user's identity, and the Issuer cannot see where the credential is being used.
* **Deliberate Rejection of JAR:** In code, **EU-AV explicitly drops the HAIP JAR requirement**. Because the AV ecosystem is inherently decentralized and lacks a master Relying Party Trust List, an attacker could easily obtain a valid certificate from a rogue CA and substitute a legitimate JAR with a malicious one.
* **Protocol Priority:** Prioritizes ISO/IEC 18013-7 Annex C (DC API) for seamless, platform-mediated presentation, utilizing Annex B (standard OpenID4VP) strictly as a fallback mechanism.
